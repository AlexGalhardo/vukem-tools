# Git and branches

- Work on a branch other than `main` for anything that will be pushed. `main` is kept in sync with
  `origin/main`; check with `git fetch origin && git rev-list --left-right --count main...origin/main`.
- Commits follow `.claude/rules/commits.md` (Conventional Commits, English, scope from the list).
  One logical change per commit; the body carries `Refs: <epic>` or the ROADMAP task.
- Stage explicit paths. Never `git add -A` or `git add .`: the tree may hold build output.
- A release is one draft pull request from `release/vX.Y.Z` into `main`: linear commits, no merge
  commit, at most 100 (GitHub's limit for a rebase merge), the last one `chore(release): vX.Y.Z`
  with the generated `CHANGELOG.md` section and the `package.json` bump. Open it only when the
  owner asks.
- Never without an explicit request: `git push`, `git tag`, `git stash`, `git checkout -- .`,
  `git reset --hard`, `git commit --amend` on a pushed commit, force pushes. The `guard-bash.mjs`
  hook blocks several of these.
- Never move a pushed tag, and push version tags one at a time (`.claude/rules/changelog.md`).
- `CHANGELOG.md` is generated by git-cliff; never edit it by hand.
- The dependency upgrade of vukem is its own commit: `build(deps): require vukem vX.Y.Z`, with the
  output of the wide test run in the body.
- Worktrees and parallel branches need an explicit yes from the owner for that task.
- Never edit the `vukem` repository from here.

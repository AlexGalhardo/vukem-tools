# ROADMAP

Every tool and every piece of infrastructure vukem-tools will have, as checkable work. This is the
project's working document: tick items as they land, and never tick one whose quality asserts do
not hold.

Decisions behind this plan: [docs/brainstorming.md](docs/brainstorming.md).
Engine and licence research: [docs/web-research.md](docs/web-research.md).

## How to use this file

- `[ ]` not started · `[~]` in progress · `[x]` done and verified.
- Three levels: **task** → subtask → microtask. A task is only `[x]` when every child is `[x]`
  **and** its **Quality asserts** block holds.
- **Quality asserts** are the definition of done for that task. They are verifiable with a command
  or an observation, never with an opinion. If an assert cannot be checked, it is written wrong.
- Phases are ordered. S1 must be complete before S2, S3 and S4 start, because they all plug into
  its queue, storage and auth.
- Finishing a phase triggers the framework-feedback ritual in
  [§ Framework feedback](#framework-feedback). That step is not optional.

## Global quality gates

These hold for every commit in every phase.

- [ ] `go build ./...`, `go vet ./...` and `golangci-lint run` clean
- [ ] `go test -race -count=1 ./...` green
- [ ] `bun run build` green for the Inertia frontend; `bunx tsc --noEmit` clean
- [ ] `npx markdownlint-cli2` clean
- [ ] Conventional Commits, validated by the `commit-msg` hook and by CI on pull requests
- [ ] `CHANGELOG.md` generated by git-cliff, never edited by hand, every entry linking its commit
- [ ] SemVer tags `vX.Y.Z`, pushed **one at a time** (GitHub creates no push event for more than
      three tags in a single push, so the release workflow would never run)
- [ ] No `//nolint`, no skipped test and no silenced error added to make a check pass
- [ ] Tab indentation, width 4, per `.editorconfig` (spaces only where the format demands it, such
      as YAML)
- [ ] Every new engine or library appears on the `/licenses` page with its exact licence before the
      feature that uses it ships
- [ ] Every third-party GitHub Action pinned to a full commit SHA (see `.claude/rules/ci.md`)

### S1.6 Job pipeline

- [ ] Queue on `vukem/queue`
  - [ ] A `Job` record with status `pending | running | finished | error | cancelled`, progress

  - [ ] One documented error taxonomy, defined once in Go and surfaced identically in the API, the

  - [ ] Retries with backoff; a failed job keeps its last error
  - [ ] Idempotency: the same input plus the same options returns the existing job instead of
        starting a second one (`vukem/api` idempotency)
  - [ ] Cancellation propagates to the subprocess by killing its process group
- [ ] Worker
  - [ ] A pool sized from the container's CPU quota, not from the host's CPU count
  - [ ] `exec.CommandContext` for every engine, with a per-tool timeout
  - [ ] `setrlimit` before `exec`: `RLIMIT_AS`, `RLIMIT_CPU`, `RLIMIT_FSIZE`, `RLIMIT_NPROC`

  - [ ] Progress parsed from `ffmpeg -progress pipe:1` and from yt-dlp's JSON lines, never scraped

- [ ] Progress delivery
  - [ ] SSE stream per job through `vukem/sse`, with heartbeat and `Last-Event-ID` resume

- A job that exceeds its timeout ends `error` with `error_type` set, not hung

## Phase S2 — Pixels → SVG

Independent of S3 and S4. Target version: `v0.2.0`.
Design and algorithm: [docs/web-research.md § 7](docs/web-research.md).

### S2.1 Core conversion library

- [ ] Package `internal/pixelsvg`, pure Go, no cgo, no external binary
  - [ ] Decode through `image` from the standard library: PNG, GIF, JPEG, plus WebP via
        `golang.org/x/image/webp`
  - [ ] Colour handling
    - [ ] Optional quantisation: median cut (`soniakeys/quant`) and octree
          (`delthas/octreequant`), capped at 256 colours
    - [ ] Colour tolerance that merges near-identical neighbours, with a documented distance metric
    - [ ] Alpha: emit `fill-opacity`, or drop fully transparent pixels, selectable
  - [ ] Region labelling
    - [ ] Union-find over horizontal runs, one pass per row
    - [ ] Correct 4-connected merging with the previous row
  - [ ] Output modes
    - [ ] `square`: one `<rect>` per pixel
    - [ ] `rect` (default): greedy horizontal run merge, then vertical merge into maximal
          rectangles
    - [ ] `contour`: Moore-neighbour boundary tracing per region, holes handled in a second pass,
          simplified with Douglas-Peucker (`paulmach/orb/simplify`)
  - [ ] SVG writing
    - [ ] Streamed into a `bufio.Writer`, never built as one big string
    - [ ] Grouped by colour in `<g fill="...">` so each colour is written once
    - [ ] `viewBox` set, `shape-rendering="crispEdges"`, no unused namespace, no editor cruft
    - [ ] `<use>` for repeated shapes where it actually shrinks the output
  - [ ] Limits
    - [ ] Reject input above **2048 × 2048** with a message naming the limit and the actual size
    - [ ] Reject above the colour cap with the same clarity
- [ ] Concurrency
  - [ ] Row bands processed by a bounded worker pool, fragments stitched in order
  - [ ] Deterministic output: the same input and options always produce byte-identical SVG

#### Quality asserts

- Golden-file tests for all three modes on a hand-made 8 × 8 sprite with alpha and duplicate colours
- Rendering the output with `resvg` and comparing against the source pixel grid shows zero
  difference in `square` and `rect` modes
- `contour` mode output, rasterised back, differs from the source by no more than the documented
  simplification tolerance
- A 2048 × 2048 input completes within a recorded time and peak RSS, both written into
  `docs/benchmarks.md`; `rect` mode produces an SVG that opens in Chrome and Firefox without
  freezing
- A 2049-pixel-wide input is refused with the limit stated, and the process memory does not grow
- `go test -race -count=1 ./internal/pixelsvg/...` green; `go test -bench . -benchmem` recorded
- Fuzz target over malformed image bytes finds no panic in 5 minutes

### S2.2 API

- [ ] `POST /api/v1/pixels-to-svg`
  - [ ] Multipart upload or a reference to an already uploaded file
  - [ ] Options: `mode`, `tolerance`, `max_colors`, `scale`, `keep_alpha`
  - [ ] Synchronous for small inputs, queued for large ones, with the same response shape

- A queued conversion streams progress over SSE and ends with a signed download URL

### S2.3 UI

- [ ] Page `/pixels-to-svg`

  - [ ] Live controls: mode selector, tolerance slider, colour cap, scale
  - [ ] Element count and output size shown, so the cost of each mode is visible

## Phase S3 — Download, edit and compress

Target version: `v0.3.0`.

### S3.1 Video download

- [ ] `internal/downloader` driving yt-dlp
  - [ ] Platform detection for YouTube, Instagram, X and TikTok from the URL, with a restricted
        extractor set per platform; the `generic` extractor is never enabled
  - [ ] Metadata endpoint: title, uploader, duration, thumbnail, available formats, estimated size
  - [ ] Download MP4 (best or smallest) or MP3, optionally compressed afterwards, delivering
        whichever file is smaller and reporting the saving
  - [ ] Clips mode: consecutive segments of at most 60 seconds, downloadable individually or as a
        `.zip`
  - [ ] Progress parsed from yt-dlp's structured output, mapped onto the job's phase and percentage
  - [ ] Cookie file, PO-token provider and sleep/retry settings all configurable, and their
        absence degraded gracefully rather than crashing
  - [ ] The size cap enforced from the estimate before the download starts, and again on the
        finished file
- [ ] Errors explained in plain English, mapped from the taxonomy: out of memory, disk full,
      platform block, unsupported URL, age-restricted, private, too large

#### Quality asserts

- Every error type reachable in a test with a fixture, including the platform-block path
- A download of a known public video produces a playable file whose duration matches the metadata
- Clips are at most 60 seconds and the `.zip` entry count matches the reported clip count
- Cancelling a download kills yt-dlp and ffmpeg and leaves no temporary file behind
- yt-dlp's version is logged at startup and surfaced on the deep readiness check
- The README states that downloading may breach a platform's terms of service and that the user is
  responsible

### S3.2 Cut and crop

## Phase S4 — Image, video and audio conversion

Target version: `v0.4.0`.

### S4.1 Image conversion

- [ ] `internal/image` driving libvips
  - [ ] Convert between JPEG, PNG, WebP, AVIF, JXL, HEIC, GIF, TIFF, BMP, ICO
  - [ ] Shrink-on-load for JPEG; sequential access mode for large inputs
  - [ ] Per-format quality and effort options, with sane defaults per format
  - [ ] ICC handling: convert to sRGB before stripping metadata
  - [ ] EXIF stripped by default, with an opt-in to keep it, and the privacy implication stated in
        the UI
  - [ ] ImageMagick fallback for PSD and anything libvips cannot read, behind a restrictive policy
- [ ] Format support surfaced by the API, not hard-coded in the frontend

#### Quality asserts

- A matrix test converts a fixture of each input format to each supported output and asserts the
  result decodes, with the expected dimensions
- Peak RSS for a 2K image conversion stays under a recorded ceiling, proven by a benchmark
- A file claiming to be PNG but containing JPEG bytes is handled by the detected type
- An image with an embedded colour profile keeps its appearance after conversion, asserted by a
  pixel-difference threshold

### S4.2 Image compression and optimisation

- [ ] Lossless chain: `oxipng` for PNG, `jpegtran` for JPEG, `gifsicle -O3` for GIF
- [ ] Lossy chain: `cjpeg`/`cjpegli` for JPEG, `pngquant` for palette PNG, `cwebp`, `avifenc`,
      `cjxl`
- [ ] A single "make this smaller" entry point that picks the chain from the detected type and
      reports what it did
- [ ] Every optimiser pinned, and its licence on `/licenses` (`jpegoptim` and `gifsicle` are GPL,
      `pngquant` is GPL-or-commercial)

#### Quality asserts

- Every chain produces a file that is smaller or the original is returned unchanged with a note
- Lossless chains are verified lossless: decoded pixels are byte-identical to the source
- Lossy chains record the SSIM or `ssimulacra2` score of a fixture, and a regression fails the test
- The reported "what it did" string names the actual tools used

### S4.3 Image editing

- [ ] Resize (fit, fill, exact, with and without upscaling), crop, rotate, flip
- [ ] Watermark: image and text, with position, opacity and margin
- [ ] Thumbnail and multi-size output through `vukem/contrib/imaging`
- [ ] Batch: the same operation applied to many files, delivered as a `.zip`

#### Quality asserts

- Geometry is asserted numerically for every mode, including odd dimensions
- A watermark is present at the requested position, asserted by sampling pixels
- A batch of 50 images runs within a recorded time with bounded memory, and a single failure does
  not fail the batch

### S4.4 Video and audio conversion

- [ ] Video: MP4 ↔ WebM ↔ MKV ↔ MOV, with CRF ladders per codec from the research document
- [ ] Video → GIF using the two-pass palette filter, with `gifski` as an optional higher-quality
      path (confirm its licence first)
- [ ] Audio: MP3, WAV, FLAC, Opus, AAC, with bitrate and quality options
- [ ] Extract audio from video; replace a video's audio track
- [ ] Loudness normalisation with `loudnorm`, two-pass when accuracy matters
- [ ] Thumbnail and sprite-sheet extraction

#### Quality asserts

- Every conversion's output is validated with ffprobe: container, codecs, duration, resolution
- A GPL-build-only codec path fails with a clear message on an LGPL build, proven by a test that
  fakes the build flags
- Encoding presets are recorded with wall-clock and output size for a reference clip, in
  `docs/benchmarks.md`
- A 500 MB input converts without the container being OOM-killed, with the worker's memory ceiling
  recorded

### S4.5 Transcription

- [ ] `internal/transcribe` driving whisper.cpp
  - [ ] Model pinned and downloaded at build time, not at runtime
  - [ ] Output SRT and VTT; language auto-detection with a manual override

## Phase S5 — Deferred tools

Everything the owner wants eventually, kept here so it is not forgotten. Each becomes its own
phase with its own asserts when it is picked up; the engines are already researched.

- [ ] **Sprite sheet and frame atlas** — split a sheet into frames, build a sheet from frames,
      export the JSON metadata that game engines expect. Directly serves the game-asset goal.
- [ ] **Archives** — ZIP, TAR, GZ, XZ, ZSTD, BR create and extract (`mholt/archives`,
      `klauspost/compress`); 7z write through `7zz`; RAR **read only**, because the unRAR licence
      forbids recreating RAR compression.
- [ ] **PDF structural operations** — merge, split, rotate, watermark, encrypt, decrypt, page
      extraction (`pdfcpu`, `qpdf`); PDF → images (`pdftoppm`); images → PDF (`img2pdf`);
      PDF → text and Markdown.
- [ ] **OCR** — scanned PDF → searchable PDF with OCRmyPDF and Tesseract.
- [ ] **Office → PDF** — Gotenberg, or `unoserver` with a pool of per-worker LibreOffice profiles.
      Last, because it adds roughly 1 GB to the image and is the most failure-prone.
- [ ] **Data formats** — CSV ↔ JSON ↔ XML ↔ XLSX (`excelize`), Parquet later.
- [ ] **Fonts** — TTF ↔ OTF ↔ WOFF ↔ WOFF2 with `fonttools`, plus subsetting.
- [ ] **Ebooks** — EPUB/MOBI/AZW3 ↔ PDF with Calibre (GPL-3.0).
- [ ] **QR codes** — generation with `libqrencode`.
- [ ] **3D and CAD** — only if the asset workflow demands it; every usable engine is GPL and large.

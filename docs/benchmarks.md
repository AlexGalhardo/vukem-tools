# Benchmarks

Recorded numbers, so a claim about speed, size or memory can be checked instead of believed.
`.claude/rules/go.md` requires a measurement before any performance claim, and `ROADMAP.md` makes
several of these numbers quality asserts.

How to reproduce a row is part of the row. A number without its command is not a benchmark.

## S4 media conversion

Every number below was measured **inside the production image**, not on a development machine.
libvips is not installed on the owner's Windows host and the engine sandbox is Linux-only, so a
figure taken outside the image would measure a different binary under no limits.

The harness, for every row:

```bash
for p in ffmpeg video audio image; do
  GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go test -c -o /tmp/t/$p.test ./internal/$p/
done
docker run --rm --cpus 2 -m 1g -v /tmp/t:/t:ro --entrypoint sh vukem-tools:local -c \
  'cd /app/work && cp /t/*.test . && for p in image video audio; do
     ./$p.test -test.run XXX -test.bench . -test.benchmem -test.benchtime 1x; done'
```

`--cpus 2` is the point of the invocation: it gives the container a CPU quota, which is what
`internal/cpu` reads and what every thread bound in these packages is sized from. Without it the
engines size themselves from the host's 16 cores and the numbers mean nothing.

`peakMB` is the **engine subprocess's** peak RSS, read from the kernel's rusage by
`internal/engine`. It is reported as a custom metric rather than through `-benchmem` because the
Go side never holds a frame: the `B/op` column is the harness, and it is three orders of magnitude
smaller than the pixels, which is the design working.

### Image conversion (S4.1, S4.3) — libvips 8.16.1

| Case | Wall clock | Engine CPU | Peak RSS | Go allocs |
| --- | --- | --- | --- | --- |
| 1080p JPEG → WebP | 566 ms | 628 ms | 69.0 MB | 239 KB / 308 |
| 1080p JPEG → JPEG | 334 ms | 410 ms | 46.5 MB | 236 KB / 292 |
| 2048×2048 PNG → JPEG | 534 ms | 796 ms | 52.9 MB | 276 KB / 292 |
| 2048×2048 PNG → 512-wide JPEG | 218 ms | 145 ms | 48.3 MB | 277 KB / 292 |
| 4K PNG → JPEG | 874 ms | 1453 ms | 72.8 MB | 359 KB / 293 |
| 4K PNG → 512-wide JPEG | 247 ms | 159 ms | 57.1 MB | 359 KB / 290 |

The 2K row is the ROADMAP's memory assert: **52.9 MB against a 128 MB ceiling**, enforced by
`TestPeakMemoryForA2KConversionStaysUnderTheCeiling`. The ceiling has deliberate headroom — an
ordinary libvips upgrade should not fail the build, while losing streaming costs a factor of ten
rather than a third.

Streaming is measured rather than asserted. A 4K frame is 33 MB as RGB and the whole pipeline peaks
at 72.8 MB, so no stage materialises more than about two frames. Shrink-on-load is visible in the
same table twice: the thumbnail rows cost a fifth of the engine CPU of the full-size rows on the
same input, because the JPEG decoder is asked for a reduced image instead of a full one.
`TestShrinkOnLoadIsCheaperThanAFullDecode` asserts it directly — a 3000×2000 JPEG peaks at 46.1 MB
to a 375-wide output against 64.5 MB at full size.

### A 519 MB input in a 1 GB container

| Date | Input | Output | Engine peak RSS | Container peak | OOM kills |
| --- | --- | --- | --- | --- | --- |
| 2026-10-18 | 519 MB, 7 s of raw 1080p yuv420p in NUT | 720p H.264 MP4 | **311.6 MB** | 815 MB | **0** |

Run through `video.Convert`, not by invoking ffmpeg by hand, so the argument building, the thread
bounds and the progress parsing are all inside the measurement:

```bash
docker run --rm --cpus 2 -m 1g -v /tmp/t:/t:ro --entrypoint sh vukem-tools:local -c '
  cd /app/work
  ffmpeg -nostdin -hide_banner -loglevel error -nostats -y     -f lavfi -i "testsrc=duration=7:size=1920x1080:rate=25"     -c:v rawvideo -pix_fmt yuv420p -threads 2 -f nut big.nut
  cp /t/video.test .
  VUKEM_TOOLS_LARGE_INPUT=/app/work/big.nut ./video.test -test.run ALargeInput -test.v
  cat /sys/fs/cgroup/memory.events /sys/fs/cgroup/memory.peak'
```

The input is uncompressed on purpose: the assert is about the input's **size**, and a 519 MB H.264
file would be two hours of video and a test about duration instead.

`oom_kill 0` is the assertion. The 815 MB container peak is mostly page cache for the 519 MB file
being read, which is reclaimable and is why the container survives at 1 GB with an engine that
peaks at 312 MB. The engine figure is the one to size a worker from.

The test is opt-in behind `VUKEM_TOOLS_LARGE_INPUT`, because generating the fixture takes longer
than the rest of the package's suite and committing half a gigabyte is out of the question. It is a
recorded manual verification; the CI gate for the same property is the next section.

### Memory does not scale with the input's length

One large file suggests the property; this measures it. `TestMemoryDoesNotGrowWithTheInputsLength`
converts a 2 s and a 20 s clip of the same shape — ten times the input — and fails if the longer
one costs more than a quarter extra. A pipeline that buffered would be close to ten times.

Both the ceiling tests run in the image as part of the ordinary suite:

```bash
docker run --rm --cpus 2 -m 1g -v /tmp/t:/t:ro --entrypoint sh vukem-tools:local -c \
  'cd /app/work && cp /t/*.test . && for p in ffmpeg video audio image; do ./$p.test; done'
# ffmpeg PASS / video PASS / audio PASS / image PASS
```

### Worker memory requirement

The highest engine peak recorded here is **399 MB**, for AV1 at 720p. Conversion concurrency is
`internal/cpu`'s limit, so a two-CPU worker may run two conversions at once: a worker that encodes
AV1 needs roughly **1 GB** of memory allowance, not the 512 MB a glance at the image rows would
suggest. H.264, H.265 and VP9 all fit in half that.

### Peak memory against page count

ROADMAP S6.6 asks that a watermark on a 500-page document be applied in one pass with peak memory
independent of the page count. Both halves hold, and the distinction between the two memory
columns above is why the figures are reported separately:

- **Peak RSS is flat.** 11.9 MB at 10 pages, 11.8 MB at 50, 12.1 MB at 500 — a 50-fold increase in
  pages moves the high-water mark by about 2 %, which is noise against the Go runtime's own
  baseline. Each size is measured in its own process, because `VmHWM` never falls and a single
  process would report the largest run's figure for all three.
- **Cumulative allocation is not flat**, and should not be read as if it were: `B/op` is bytes
  allocated over the whole operation, not bytes live. It grows by about 6.3 kB per page, which is
  the page dictionary qpdf prints as JSON while the page geometry is read. That memory is freed as
  the decoder walks past it, which is exactly why the peak does not move.

One pass means one engine invocation: the stamp document is written page by page and composited by
a single `qpdf --overlay`, so a 500-page watermark is one subprocess rather than 500.

### What the figures say about the engine choices

- **Structure is cheap because nothing is re-rendered.** A 10-document merge and a 20-way split are
  both about an eighth of a second, because qpdf edits the object graph. Compression is in the same
  range only because the fixture is text; Ghostscript re-renders every page, and on a document of
  photographs it is an order of magnitude slower — the appearance test's fixture, four pages of
  2000 × 1400 photographs, compresses 698 kB to 74.5 kB in about 1.1 s.
- **Rasterising is the expensive one**, and it is the one that parallelises: each page is its own
  `pdftoppm`, bounded by `internal/cpu.Limit()` rather than by the host's core count. The 226 ms
  for 10 pages at 150 DPI is with 16 CPUs available; on a 1-vCPU container expect it to be
  sequential.
- **The PDF writer is not the cost of anything.** 1.23 ms for 500 pages means a watermark's stamp
  document is a rounding error next to the composite, which is what justified writing it in Go
  rather than reaching for another engine.
- **Sprite sheet building** (S7.2): peak heap against frame count, which must not grow with it.

#### Peak live heap

```bash
go test -run 'TestPeakMemory' -v -count=1 ./internal/spritesheet/
```

| Date | Sheet | Frames | Peak heap in use | Decoded sheet alone |
| --- | --- | --- | --- | --- |
| 2026-10-18 | 2048 × 2048 | 64 | 19.4 MiB | 16.0 MiB |
| 2026-10-18 | 2048 × 2048 | 256 | 19.5 MiB | 16.0 MiB |
| 2026-10-18 | 2048 × 2048 | 1024 | 20.1 MiB | 16.0 MiB |
| 2026-10-18 | 4096 × 4096 (`MaxPixels`) | 1024 | **68.6 MiB** | 64.0 MiB |

Sixteen times the frames costs 0.7 MiB more live heap, which is what proves the design: frames are
encoded into the archive one at a time through crops that share the decoded sheet's own pixel
buffer, so the cost is one sheet plus one encoder rather than one sheet plus every frame. At the
area limit the overhead above the decoded sheet is 4.6 MiB.

**This is Go's live heap, not the container's RSS.** The two are not the same number and this host
is Windows, so an RSS figure measured here would not be comparable with the Linux container's.
The ROADMAP's S7.1 assert is recorded as met on the heap figure and the ratio; the container RSS
row is owed and will be taken on Linux when the tool is deployed. Saying so beats presenting a
host number as a container number.

Under `-race` the same 4096 × 4096 split peaks at 102 MiB rather than 68.6 MiB, because the
detector holds shadow state per allocation. The test widens its bound in a race build rather than
skipping, so a real regression is still caught either way.

#### What the first measurement found

The first run of this benchmark was **1 504 ms and 1.28 GB allocated over 16 823 313 allocations**
for the 4096 × 4096 case — close to one allocation per pixel. Two causes, both found by measuring
rather than reading:

- `image.Image.At` returns a `color.Color` interface, so every pixel read boxed a colour onto the
  heap. Resolving the concrete image type once and indexing `Pix` directly (`internal/spritesheet`
  `pixels`) removed it.
- The per-frame crop was an `image.Image` adapter, which is correct but defeats `png.Encode`'s
  type switch onto its fast path, sending every pixel back through the boxing `At` call. Re-basing
  the concrete `SubImage` to the origin instead keeps both the shared pixel buffer and the fast
  path.
- `png.Encoder` was then still allocating its compressor per frame; giving it a `BufferPool` cut
  the remaining 1.21 GB to 70 MB.

Net: **3.8 × faster, 18 × less allocated, 822 × fewer allocations.** Recorded because the ROADMAP
asks for a measurement rather than a claim, and because the first number was the one that would
have shipped.

## A caveat on every `MaxRSS` figure here

The engine's peak resident memory comes from `wait4`'s rusage, and a forked child inherits the
parent's resident pages until `exec` replaces its image. So `ru_maxrss` is really
**max(the worker's own RSS at fork, the engine's peak)**, not the engine's peak alone.

It is usually harmless — the worker is far smaller than a conversion — but it is a floor, so a
small conversion's figure can be the worker's size rather than its own. It stops being harmless
under `go test -race`, where the instrumented binary is around 150 MB and every engine then
reports exactly that: `TestShrinkOnLoadIsCheaperThanAFullDecode` detects the two conversions
coming back identical to the byte and skips rather than asserting on a number that measures
nothing.

Read any engine RSS row below as an upper bound, and measure without `-race`.

## Archives

Pure Go: `archive/zip`, `archive/tar` and `compress/gzip`. No engine, no subprocess, so these are
in-process figures from `go test` rather than container figures.

Fixtures are generated by the benchmark: members of pseudo-random bytes (`i % 251`), which is
compressible but not trivially so. All-zero members would measure deflate's fast path and nothing
else.

```bash
go test -run XXX -bench . -benchmem ./internal/archive/
```

| Date | What | Result |
| --- | --- | --- |
| 2026-10-19 | `BenchmarkCreateZip` — 32 members of 64 KiB into a ZIP | **2.53 ms/op**, 1.11 MB/op, 538 allocs/op |
| 2026-10-19 | `BenchmarkCreateTarGz` — the same 32 members into a TAR.GZ | **6.36 ms/op**, 2.15 MB/op, 383 allocs/op |
| 2026-10-19 | `BenchmarkExtractZip` — that ZIP back out to disk | **4.25 ms/op**, 1.09 MB/op, 584 allocs/op |

TAR.GZ is two and a half times the wall clock of ZIP for the same members, and that is the

it cannot skip a member the way per-member deflate can, and it buys a smaller archive for it.

### Memory does not follow the archive

Two asserts in `internal/archive/bench_test.go`, written as tests because they bound a figure
rather than report one. Both sample Go's `HeapAlloc` from a goroutine **during** the extraction:
a reading taken only before and after misses a peak in the middle, which is the exact shape of the
bug they exist to catch.

The figure is Go's live heap, not the process's RSS. Every allocation on this path is the Go
runtime's, and an RSS number from one host is not comparable with the container's — so this
section does not present the one as the other.

`TestPeakMemoryDoesNotGrowWithMemberSize` — two members, the member size growing 128×:

| Member size | Peak live heap |
| --- | --- |
| 64 KiB | 1.4 MiB |
| 1 MiB | 1.4 MiB |
| 8 MiB | 1.4 MiB |

Flat to three figures across a 128× range. This is the one that proves a member's bytes are
streamed: a design that read a member whole before writing it would track the left-hand column.

`TestExtractionNeverHoldsMuchOfTheArchive` — a fixed 8 MiB total, split finer each time:

| Members | Member size | Peak live heap |
| --- | --- | --- |
| 4 | 2 MiB | 1.4 MiB |
| 16 | 512 KiB | 1.8 MiB |
| 64 | 128 KiB | 3.4 MiB |

This one is **not** flat, and the reason is worth recording rather than smoothing over. Each ZIP
member is inflated through its own `flate` reader, whose 32 KiB window and Huffman tables come to
roughly 33 KiB; sixty-four members churn about 2 MiB through the heap, and `HeapAlloc` counts
allocated-but-not-yet-swept bytes, so a peak sampled between collections sees some of that churn.
It is churn and not accumulation — the table above is what settles that — and the assert is
therefore written against a ceiling of 2 MiB plus 64 KiB per member, and against never reaching
half the archive's size.

`-benchmem`'s `B/op` cannot answer this question at all: it is every byte ever allocated during
the operation, which does grow with the member count by design. `BenchmarkExtractByMemberCount`
reports it (280 KB at 8 members, 2.17 MB at 64) so the churn is visible, not so it can be read as
a peak.

### Why there is no XZ or ZSTD row

Neither is in the standard library. Each would have cost a module and a `/licenses` entry to add a
format the four here already cover for anything sent to a web service, so neither ships;
`docs/brainstorming.md` records the decision. `git diff go.mod go.sum` over this feature is empty.

## Image compression (S4.2)

libvips only. The ROADMAP planned a chain of specialist optimisers — oxipng, jpegtran, pngquant,
gifsicle, cwebp — and that is not what shipped; `docs/brainstorming.md § 7` records why. These are
the figures that decision has to be judged against.

Fixtures are the project's gradient seed, which has structure. A flat colour compresses to nothing
whatever the encoder does and would make any of this look like it works.

```bash
go test -count=1 -run TestCompressing -v ./internal/image/
```

| Date | Input | Before | After | Saved | Mode |
| --- | --- | --- | --- | --- | --- |
| 2026-10-19 | PNG 1200×800, encoded by Go | 22 075 B | 5 717 B | **74.1 %** | lossless |
| 2026-10-19 | JPEG 1200×800 | 28 349 B | 17 234 B | **39.2 %** | lossy, SSIM 0.9977 |
| 2026-10-19 | WebP 1200×800, written by libvips | 5 370 B | 5 370 B | 0 % | returned unchanged |
| 2026-10-19 | GIF 1200×800, written by libvips | 282 344 B | 282 344 B | 0 % | returned unchanged |

The two zeroes are the point rather than a disappointment. Those fixtures were written by libvips
at its own defaults, so libvips cannot beat them, and the tool returns the original with a sentence
saying so instead of handing back a re-encode that is larger. A specialist chain would win here;
one general-purpose encoder does not, and the interface says which happened.

The JPEG figure carries an SSIM rather than a mean difference. A mean is dominated by flat areas
and stays high while an edge turns to mush, which is exactly the failure a quality regression
produces; `TestCompressingAJPEGIsSmallerAndStaysFaithful` fails below 0.95.

### The PNG row-filter bug this found

libvips's `pngsave` defaults to **no row filtering**. libpng recommends that only for
already-compressed data; on anything with structure the compressor is left with nothing to work
with. Measured on the 600 × 400 gradient fixture:

| pngsave options | Bytes |
| --- | --- |
| `compression=9` (what this service shipped) | **150 527** |
| `compression=9,filter=all` | **2 026** |
| Go's `image/png`, for reference | 2 063 |
| `compression=9,palette=true,Q=80,dither=1` | 58 982 |

Seventy-four times larger, on every PNG `image-convert` has ever written. `filter=all` is now the
default there, and `TestConvertingToPNGUsesRowFilters` is the regression test.

Two things worth keeping from the table. The filters lose on one input kind — a field of pure
noise is 235 297 B unfiltered against 240 775 B filtered, about 2 % — which is why the compression
tool runs both and keeps the smaller rather than picking one. And the palette, which is the lossy
mode, is twenty-nine times *worse* than lossless here, because dithering a smooth gradient adds
noise the compressor then has to store: that is why the lossy candidate list also contains the
lossless candidates, and why "lossy" means permission to move the pixels rather than an obligation.

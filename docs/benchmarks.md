# Benchmarks

Recorded numbers, so a claim about speed, size or memory can be checked instead of believed.
`.claude/rules/go.md` requires a measurement before any performance claim, and `ROADMAP.md` makes
several of these numbers quality asserts.

How to reproduce a row is part of the row. A number without its command is not a benchmark.

conversion engines. Phase S1.11 adds ffmpeg, yt-dlp, libvips and Ghostscript, which will dominate
the size from then on; the ROADMAP treats a later regression above 20 % as a review failure, and
this row is the baseline that makes that measurable.

## Conversion paths

Each tool lands with its own row, carrying wall-clock and peak RSS for a named fixture, per
`.claude/rules/go.md`.

### Trim: copy against re-encode (S3.2)

The fixture is generated by the benchmark itself rather than kept in the repository, so the
keyframe interval is under the test's control: 30 seconds of `testsrc` at 1280 × 720, 30 fps,
H.264 with a keyframe every second. Both benchmarks cut the same 10 seconds starting at 5 s;
`BenchmarkTrimReEncode` asks for frame accuracy, which is what forces the re-encode.

| Date | Where | `-c copy` | Re-encode | Copy as a share of the re-encode |
| --- | --- | --- | --- | --- |
| 2026-10-18 | `vukem-tools:s3` image, `--cpus 2`, ffmpeg 7.1.5 | **235 ms/op** | **2 643 ms/op** | **8.9 %** (11.2× faster) |
| 2026-10-18 | Windows host, 16 threads, ffmpeg 9.0.2 | 323 ms/op | 1 204 ms/op | 26.8 % (3.7× faster) |

```bash
# In the image, which is the figure that counts: the container has 2 CPUs.
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go test -c -o /tmp/editor.test ./internal/editor/
docker run --rm --cpus 2 -v /tmp:/t:ro --entrypoint sh vukem-tools:s3   -c 'cd /tmp && cp /t/editor.test . && ./editor.test -test.run "^$"       -test.bench BenchmarkTrim -test.benchmem -test.benchtime 5x'

# On a development machine, where ffmpeg is whatever is on PATH.
go test -run '^$' -bench BenchmarkTrim -benchmem -benchtime 3x ./internal/editor/
```

The copy's 235 ms is almost entirely process startup and the two ffprobe calls that decide the
branch — the copy itself is a few megabytes of I/O. The re-encode scales with the clip's length and
resolution, and the host row shows why the image row is the one to quote: a 16-thread machine
hides most of the encoding cost, and the container does not.

Versions follow SemVer and are in `0.x`: a minor release may break. Every version is a tag `vX.Y.Z`.

## The changelog

`CHANGELOG.md` is generated by git-cliff from Conventional Commits, in the Keep a Changelog format. Do not edit it by hand: write a good commit message instead. `feat` goes to Added, `fix` to Fixed, and `refactor` and `perf` to Changed. `docs`, `test`, `ci`, `build` and `chore` are left out.

## Cutting a release

1. Generate the section: `git cliff --tag vX.Y.Z -o CHANGELOG.md`.
2. Commit it with the version bump, with the message `chore(release): vX.Y.Z`.
3. Create an annotated tag `vX.Y.Z`.
4. Push the commit and the tag. Push version tags one at a time: GitHub creates no push event when more than three tags go up in one push, so the workflow would never run.

Never move a tag that was already pushed. If the workflow fails, fix the cause and run it again on the same tag.

## What the workflow builds

The `release` workflow runs on a version tag:

| Step | Result |
| --- | --- |
| Tests | The suite has to pass. |
| Image | `ghcr.io/alexgalhardo/vukem-tools` and `alexgalhardo/vukem-tools` on Docker Hub, with provenance. A stable version also gets `X.Y` and `latest`. |
| CLI | `vukem-tools-cli-X-Y-Z-<system>-<arch>` for Windows (amd64), Linux (amd64, arm64) and macOS (arm64). |
| Windows | The setup file and the portable zip. The workflow installs and uninstalls the setup silently to prove it works. |
| Linux and macOS | The AppImage and the dmg. |
| Checksums | `checksums.txt` for every file. |
| GitHub release | Created after the image is pushed, with the changelog section as its notes. A missing section fails the job. |

The file names carry the version with the dots turned into hyphens. See [Desktop downloads](/docs/self-hosting/desktop-downloads).

A manual run of the workflow builds the same files from any branch, without a tag and without a release, so you can test an installer before tagging. Download them from the run's artifacts. Nothing is signed.
